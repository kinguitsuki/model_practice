## 1. RAG パイプライン

### 1-1. テキスト分割（RecursiveTextChunker）

**ファイル**: [rag/chunker.py](../rag/chunker.py)

#### アルゴリズム

```
再帰的テキスト分割

入力: テキスト全文
出力: 512文字以下のチャンクのリスト

ステップ:
1. テキストが chunk_size (512) 以下なら → そのまま返す
2. 優先分割文字を探す: \n\n → \n → 。 → . → 空白 → ''
3. 見つかった文字で split()
4. チャンクが chunk_size を超えたら保存 + オーバーラップを引き継ぐ
5. 1つの部分がまだ大きい場合は次の区切り文字で再帰
```

#### なぜ固定幅ではなく再帰的分割か

固定幅分割（文字数で機械的に切る）は段落の途中で切れる。
再帰的分割は「段落 → 文 → 単語」の順で意味単位を優先するため、
埋め込みモデルの精度が上がる。

#### オーバーラップの意味

```
チャンク A: [...前半のテキスト...][最後の64文字]
チャンク B: [最後の64文字][...後半のテキスト...]
              ↑─ 重複 ─↑
```

チャンク境界をまたぐ文脈を失わないため。
「X は Y である。したがって Z が」という文で分割されても
「Y である。したがって Z が」がどちらのチャンクにも含まれる。

### 1-2. 埋め込み生成（EmbeddingModel）

**ファイル**: [rag/embedder.py](../rag/embedder.py)

#### なぜ E5 モデルを使うか

`intfloat/multilingual-e5-base` は次の点で優秀：
- **多言語対応**: 日本語・英語の混在テキストに対応
- **質の高い類似度**: 意味的に近い文書が高スコアになる
- **適切なサイズ**: 768次元、270MB程度で手元で動かせる

#### query / passage プレフィックス

E5 モデルは学習時に用途を区別するためのプレフィックスを使用している：

```python
# 検索クエリ（短い質問文）
"query: RAGとは何ですか？"

# 文書チャンク（長い説明文）
"passage: RAGとはRetrieval-Augmented Generationの略で..."
```

これにより、質問と回答が異なる文体でも高い類似度を計算できる（非対称検索）。

#### コサイン類似度の計算

```python
# ベクトルを L2 正規化（長さ = 1 に揃える）
normalize_embeddings=True

# 正規化後は内積 = コサイン類似度
# cos(θ) = A·B / (|A||B|) = A·B   (|A|=|B|=1 なので)
```

FAISS の `IndexFlatIP` は内積で検索するため、正規化されたベクトルを入れると
コサイン類似度での検索になる。

### 1-3. ハイブリッド検索（HybridRetriever）

**ファイル**: [rag/retriever.py](../rag/retriever.py)

#### 2 段階スコアリング

```
Step 1: FAISS でセマンティック検索 → top_k × 2 件取得
Step 2: キーワードマッチでスコアを加算 → 上位 top_k 件を選択

最終スコア = コサイン類似度 + (クエリとの共通単語数 × 0.02)
```

#### なぜセマンティック単独では不十分か

| 状況                                     | セマンティック | ハイブリッド |
|------------------------------------------|---------------|-------------|
| 「FAISS とは」という質問で「Pinecone」が上位に | 意味が近いため高スコア | キーワード不一致で降格 |
| 「R² スコア」という技術用語の検索         | 周辺文脈を取得 | 「R²」が完全一致なら昇格 |

## 2. ReAct エージェント

### 2-1. メインループ

**ファイル**: [agent/core/agent.py](../agent/core/agent.py)

#### 1 回のイテレーションの流れ

```
[1] スクラッチパッド（これまでの思考 + 観察）を LLM に送る
      ↓
[2] LLM が "Thought / Action / Action Input" を生成
      ↓
[3] "Final Answer:" を検出 → ループ終了、回答を返す
      ↓（なければ）
[4] Action と Action Input を正規表現でパース
      ↓
[5] ToolRegistry から該当ツールを取得して実行
      ↓
[6] 実行結果を "Observation: ..." としてスクラッチパッドに追記
      ↓
[7] 1 に戻る
```

#### スクラッチパッドの構造

```
ユーザーの質問

Thought: RAGについて検索が必要です
Action: rag_search
Action Input: RAG 仕組み 概要
Observation: 【参考資料1】RAGとは...

Thought: 十分な情報が得られました
Final Answer: RAGとは...
```

LLM は毎回このスクラッチパッド全体を受け取り、続きを生成する。

#### なぜ history を 2 回目以降クリアするか

```python
# 2 回目以降は history を空にして scratchpad だけを渡す
history = []
```

スクラッチパッド = 「このタスクの全文脈」であり、
messages 形式で重複して渡すとトークンを 2 倍消費してしまう。
ReAct の文脈は scratchpad に全て含まれているため、
messages は最初の 1 回だけ使う（過去の会話履歴）。

### 2-2. プロンプト設計

#### system プロンプトのキャッシュ

```python
# llm/claude.py
"system": [{"type": "text", "text": system, "cache_control": {"type": "ephemeral"}}]
```

同じ system プロンプトを複数回のターンで再利用する場合、
`cache_control: ephemeral` を付けると Anthropic がキャッシュを保持し、
トークンコストを最大 90% 削減できる（約 5 分間有効）。

#### 正規表現パース

```python
# Action: ツール名 を抽出
action_match = re.search(r"Action:\s*(.+?)(?:\n|$)", text)

# Action Input: を抽出（複数行にまたがる場合も対応）
input_match = re.search(
    r"Action Input:\s*([\s\S]+?)(?:\n(?:Thought|Action|Final Answer|Observation)|$)",
    text
)
```

`[\s\S]+?` は改行を含む任意の文字の最小マッチ。
次の ReAct キーワードが来るまでを Action Input として取り込む。

### 2-3. ツールの安全な実行

**ファイル**: [agent/tools/base.py](../agent/tools/base.py)

```python
def safe_run(self, tool_input: str) -> ToolResult:
    try:
        return self.run(tool_input)
    except Exception as exc:
        return ToolResult(success=False, output="", error=str(exc))
```

ツールが例外を投げても `safe_run` がキャッチして `ToolResult` に変換する。
エージェントループが例外で中断されることなく、エラーを Observation として
LLM に伝えることができる。

### 2-4. 計算機の AST サンドボックス

**ファイル**: [agent/tools/calculator.py](../agent/tools/calculator.py)

**なぜ `eval()` を使わないか**

```python
# 危険: eval() は任意のコードを実行できる
eval("__import__('os').system('rm -rf /')")  # 実行される

# 安全: AST ウォークで許可された演算子のみ評価
```

AST（抽象構文木）パースにより、四則演算と math 関数のみを
ホワイトリスト方式で許可。`import` や関数定義などは弾かれる。

## 3. 会話メモリ

**ファイル**: [agent/core/memory.py](../agent/core/memory.py)

### スライディングウィンドウ

```python
# 直近 max_window × 2 件のメッセージだけ保持
recent = self._history[-(self._max_window * 2):]
```

デフォルトは 10 ターン（user × 10 + assistant × 10 = 20 メッセージ）。
古い会話は自動的に破棄されるため、長時間使ってもトークン超過しない。

### エージェントが長期記憶を持つ方法

このプロジェクトでは短期メモリのみ実装しているが、
長期記憶を持たせるには RAG の仕組みを使う：

1. 会話を終えたら重要な情報を `knowledge_base/` に書き出す
2. インデックスを再構築する
3. 次の会話で RAG 検索により「過去の記憶」を参照できる

## 5. ナレッジベースの拡張方法

任意の形式でドキュメントを追加できる。

```bash
# 1. ドキュメントを置く
cp your_document.pdf knowledge_base/

# 2. インデックスを再構築
python main.py --mode build-index

# 3. 質問する
python main.py
# → "あなた: your_document の内容を教えて"
```

対応形式：
- `.md` / `.txt` — テキストドキュメント
- `.pdf` — PDF（pypdf で解析）
- `.csv` — 表形式データ（pandas で文字列化）
